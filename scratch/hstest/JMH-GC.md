# shape 定稿环优化：JMH + `-prof gc` 的 A/B 对照（结论：**有效**）

## 背景

用**手写计时循环**测这次优化时，同一版本波动 ±30%（N=1600 得到
55.8 / 61.9 / 66.3 / 68.9 / 74.1 ms），我甚至据一次读数误判"优化后更慢"。

改用 **JMH + `-prof gc`** 测**分配量**（`gc.alloc.rate.norm`，B/op）后，
效应立刻清晰 —— 因为这次优化的本质就是**少分配临时对象**，
分配量才是它的正确验收指标，墙钟时间不是。

## 方法

必须与**改前代码**对照，不能只报当前绝对值（与 ② 的 O(1) 改动同一手法）：

```bash
# A：当前（优化后）
./gradlew jmh            # includes=AlignBenchmark, profilers=gc

# B：改前
git checkout 1c276116 -- hotswap-agent/src/nipx/LambdaAligner.java
./gradlew jmh
git checkout HEAD -- hotswap-agent/src/nipx/LambdaAligner.java   # 恢复
```

（核对：改前版 `shapeKey` 计数为 0、`String.join` 计数为 1；改后相反。）

## 结果

| N | 改前 `gc.alloc.rate.norm` | 改后 | **降幅** |
|---|---|---|---|
| 100 | **4,131,107 B/op**（4.13 MB） | **2,406,586 B/op**（2.41 MB） | **≈ 42%** |
| 400 | **9,717,929 B/op**（9.72 MB） | **7,968,101 B/op**（7.97 MB） | **≈ 18%** |

（改前数值取两次测量 4,131,107 / 4,125,830 与 9,717,929 / 9,652,770 的较大者；
改后 2,406,586 / 2,377,535 与 7,968,101 同。）

### 时间（噪声大，只作参考）

| N | 改前 | 改后 |
|---|---|---|
| 100 | 9.477 ms/op | 8.077 ms/op |
| 400 | 21.575 ms/op | 37.626 ms/op ← **明显是噪声** |

**N=400 的时间"改后更慢"显然不可信**（分配量明明降了 18%），
再次印证：这个量级下**时间不可作为判据**。

## 结论

- ✅ **shape 优化确实有效**：每次 `align` 减少 **18%–42%** 的分配量；
- ✅ 该效应**时间测不出、分配量测得出** —— 选对指标比提高精度更重要；
- ✅ 行为未变（`./gradlew check` 全绿）。

## 记账

- JMH 配置临时降到 `iterations = 2 / warmupIterations = 2 / fork = 1` 以在预算内完成；
  完整配置建议回到 3/2/1 或更高。
- N=1600 的两项数据本轮仍未取全（输出含大量构建日志，提取易受编码干扰）。
- `jmh { jvm }` 必须是 **JDK 25**（与依赖一致）；设 `options.release = 21`
  会让 Gradle 拒绝消费用 25 编的依赖。
